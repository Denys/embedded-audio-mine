## 1. Dylan-Hackett / Thaumazein — PASS

Repository:

```text
https://github.com/Dylan-Hackett/Thaumazein
```

### Technical summary

`Thaumazein` is a Daisy Seed polyphonic Eurorack voice. The README describes a synth engine combining Plaits-style macro-oscillators, per-voice envelopes, an arpeggiator, and an effects chain including delay, biquad filters, and Freeverb. The current task list explicitly includes Clouds granular integration, further CPU optimization, UI refinement, and artifact investigation.

### Why it matters

This is the best item today because it exposes several real embedded-audio integration problems at once:

```text
Daisy Seed / STM32H750
→ QSPI XIP app flow
→ Plaits-derived voice rendering
→ touch + ADC control surface
→ arpeggiator
→ Clouds granular processor integration
→ CPU metering / display update pacing
```

It is less polished than a released module, but it is more useful than another small effect sketch because it shows the friction points around Mutable-derived DSP on Daisy: sample-rate/block-size coupling, QSPI boot layout, memory buffers, control processing cadence, and UI/touch hardware.

### Implementation highlights

- Build targets include `make flash-stub`, `make flash-app`, and `make program-dfu`.
- The full app is intended to execute-in-place from QSPI at `0x90040000`, with README-level vector/reset sanity checks.
- Audio architecture is split into `ProcessUIAndControls`, `UpdateArpState`, `RenderVoices`, and `ApplyEffectsAndOutput`.
- The audio callback performs 1 ms control/UI service, CPU-meter block timing, voice rendering, Clouds preparation, and output update.
- Clouds integration uses fixed buffers: one ~118 kB working block plus ~65 kB CCM block.
- The interface layer uses 12 ADC channels, an MPR121 touch sensor, 12 touch LEDs, CPU load metering, and an arpeggiator callback path.
- Hardware init sets the audio rate to 32 kHz to lower CPU/memory pressure, then initializes memory-mapped QSPI state storage.

### Hardware/electronics notes

This is a firmware-heavy repo, not a complete public hardware package. Still, the hardware boundary is specific enough to be useful:

- Daisy Seed target.
- ADC channel map for knobs/pads on pins 15–25 and 28.
- MPR121 capacitive touch sensor path.
- 12 LED GPIO outputs on Daisy Seed D1–D14 subset.
- QSPI memory-mapped boot/application assumptions.
- Clouds/Plaits memory placement considerations.

The main electronics follow-up would be to recover or create the matching front-panel schematic and verify ADC/touch signal conditioning, input protection, and LED current paths.

### Platform relevance

Daisy Seed, libDaisy, DaisySP, Mutable Instruments Plaits/Clouds-derived DSP, QSPI XIP on STM32H750, MPR121 touch UI, arpeggiated Eurorack voice design.

### Adaptation ideas

- Use the QSPI stub/app notes as a checklist for large Daisy applications that no longer fit normal internal-flash assumptions.
- Reuse the explicit sample-rate/block-size audit section before porting other Mutable engines.
- Split your own Daisy Field/Seed synth into similar `control → arp/state → render voices → post-FX` phases.
- Treat the MPR121 + LEDs + arpeggiator path as a starting point for a touch-key Eurorack controller.
- Study the Clouds buffer sizing before attempting granular processing on Daisy with additional polyphony.

### Quick engineering assessment

Strong **PASS**.

Not `STRONG_PASS`: the repo reads like an active integration bench, not a finished build package. There are signs of removed/reworked delay code, active Clouds bring-up, and possible artifact work still open. That said, the implementation detail is high enough to be worth mining immediately.

### Caveats / verification gaps

- No compile/flash test was run in this automation.
- Hardware design files were not found in the inspected paths.
- Clouds output is currently reduced to mono in the inspected output path.
- The README contains project-management/task content mixed with build notes, so exact maturity should be verified before hardware work.

## 2. lewis1286 / quad-boids-mixer — PASS

Repository:

```text
https://github.com/lewis1286/quad-boids-mixer
```

### Technical summary

`quad-boids-mixer` is a Daisy Patch quadraphonic mixer. Two audio inputs are positioned in a four-channel field by CV inputs, while two additional audio inputs follow predefined internal movement paths such as circular and figure-8 trajectories.

### Why it matters

This is a compact but useful spatial-audio reference for Daisy Patch:

```text
4 audio inputs
+ 4 audio outputs
+ CV-controlled X/Y position
+ internally automated paths
+ OLED position feedback
+ interrupt-safe audio/control split
```

The useful part is not only quad panning. The code documents a practical embedded split between audio interrupt context and main-loop/UI context, with volatile bridge variables, smoothing, encoder event draining, and bounded path update cadence.

### Implementation highlights

- Dependency layout is explicit: `libDaisy`, `DaisySP`, and the project live as sibling directories.
- Build/flash flow is `make clean && make`, then `make program`.
- CV1/CV2 control X/Y position of input 1.
- CV3/CV4 control X/Y position of input 2.
- Inputs 3 and 4 use internal movement paths.
- Encoder selects or edits movement behavior.
- Daisy Patch I/O mapping is 4-in / 4-out.
- Audio callback handles ADC/digital refresh, encoder event capture, position smoothing, quad-gain computation, and sample mixing.
- Main loop handles slower UI/path/display work.
- The pan law implementation is visible in a separate `QuadMixer.h`.

### Hardware/electronics notes

Target is the stock Electrosmith Daisy Patch, so there is no custom analog front end. From an electronics perspective, the value is in using the full Patch I/O set as intended:

```text
IN1–IN4  → spatial sources
OUT1–OUT4 → FL / FR / RL / RR
CTRL1–CTRL4 → CV-position inputs
encoder/OLED → path and visual feedback
```

The firmware assumes Daisy Patch signal conditioning and does not solve external CV protection or level scaling itself.

### Platform relevance

Daisy Patch, quadraphonic audio, CV-controlled panning, spatial modulation, real-time-safe UI/audio split, embedded OLED feedback.

### Adaptation ideas

- Convert it into a 4-output Eurorack spatializer for OXI-driven CV movement.
- Reuse the interrupt/main-loop bridge pattern for Daisy Field projects with display + audio.
- Replace internal paths with LFOs, envelopes, chaos, or MIDI CC motion.
- Compare its bilinear corner law against equal-power VBAP-like panning for speaker layouts.
- Lift the smoothing and display-mirroring pattern to avoid UI/audio disagreement.

### Quick engineering assessment

Solid **PASS**.

It is small, build-described, and immediately understandable. The caveat is that it is a specialized utility rather than a broad synth/effects platform.

### Caveats / verification gaps

- No compile/flash test was run.
- No custom hardware evidence is expected because it targets Daisy Patch.
- The code comments say “equal-power” in one place while the inspected implementation uses linear bilinear gains. Treat the actual code as the source of truth.

## 3. algomusic / M16 — REF_PASS

Repository:

```text
https://github.com/algomusic/M16
```

### Technical summary

`M16` is a 16-bit Arduino audio synthesis library for ESP8266, ESP32 variants, and Raspberry Pi Pico 2. The README says it supports selected microcontrollers plus I2S audio DACs/ADCs and ESP32 internal DACs where available.

### Why it matters

This is useful as a cross-MCU audio framework reference, especially for ESP32/Pico 2 timing problems that are often hidden in sketch-level demos:

```text
Arduino API
→ audioUpdate() callback model
→ I2S DAC/ADC support
→ ESP32 / ESP32-S2 / ESP32-S3 / Pico 2 targets
→ dual-core synchronization notes
→ PSRAM diagnostics
```

The strongest part is not the oscillator API; it is the operational detail around dual-core audio generation, sample ordering, nonblocking atomic guards, PSRAM checks, and warning that Wi-Fi/file I/O can disrupt timing-critical audio.

### Implementation highlights

- README-level default I2S pin mappings are provided for ESP8266, ESP32, and Pico 2.
- `seti2sPins()` supports changing ESP32/Pico pin assignments.
- User sketches provide `audioUpdate()`, which ends by calling `i2s_write_samples(leftVal, rightVal)`.
- The README explicitly warns that timing-critical audio may not coexist cleanly with Wi-Fi or file I/O.
- Header code includes dual-core ESP32/RP2040/RP2350 handling assumptions.
- Nonblocking and blocking atomic guard macros are provided for shared state in audio paths.
- The comments document specific race/order risks around dual-core ESP32 I2S sample output.
- PSRAM diagnostics and safe allocation helpers are included for ESP32.

### Hardware/electronics notes

The library is not a board design. Hardware usefulness is in the I2S/DAC/ADC assumptions:

- ESP32 default external I2S pins: BCLK GPIO16, LRCLK GPIO17, DOUT GPIO18, DIN GPIO21.
- Pico 2 output defaults: BCLK GPIO16, DOUT GPIO18, WS implied as BCLK+1.
- Pico 2 input defaults: BCLK GPIO20, DIN GPIO19, WS implied as BCLK+1.
- It explicitly notes that some I2S DAC/mic boards require extra grounded terminals.

For real products, this still needs board-specific clocking, analog output filtering, power/noise review, and library-timing validation under intended UI/MIDI/Wi-Fi load.

### Platform relevance

ESP32, ESP32-S2/S3, ESP8266, Raspberry Pi Pico 2 / RP2350, Arduino audio, I2S DAC/ADC, embedded synth libraries, dual-core real-time audio.

### Adaptation ideas

- Use M16 as a comparison point against Mozzi, ML_SynthTools, ESP-IDF native audio, and Pico SDK audio.
- Mine the dual-core synchronization comments before writing ESP32 audio callbacks.
- Reuse the PSRAM diagnostics idea in sample players, loopers, and wavetable engines.
- Use its `audioUpdate()` model for quick ESP32/Pico 2 algorithm sketches, but validate timing before treating it as product infrastructure.
- Compare Arduino-core convenience versus deterministic ESP-IDF/Pico SDK control.

### Quick engineering assessment

Correct lane: **REF_PASS**.

It is broad and reusable, but not a single finished instrument or module. Good as an architecture/reference layer; not something I would accept blindly for a timing-sensitive ESP32 product without profiling.

### Caveats / verification gaps

- No examples were compiled.
- License is CC BY-NC-SA 4.0, so it is not drop-in for commercial firmware without checking compatibility.
- Arduino-core timing and Wi-Fi/file-I/O interaction need measurement on the target board.
- The code comments are unusually detailed; still verify actual current implementation before relying on the comments alone.

## 4. Farmer2K5 / daisy-sdram-delaylines — REF_PASS

Repository:

```text
https://github.com/Farmer2K5/daisy-sdram-delaylines
```

### Technical summary

`daisy-sdram-delaylines` provides SDRAM-backed delay-line classes for Daisy Seed, intended for long-delay and reverb work. It extends DaisySP-style delay-line patterns to external SDRAM using either externally supplied buffers or internal SDRAM allocation.

### Why it matters

This is exactly the kind of low-level support code that becomes important once Daisy projects move beyond short delays:

```text
DaisySP DelayLine pattern
→ external SDRAM buffer
→ allocator-backed SDRAM delay
→ long delay / reverb memory budget
→ measured SRAM and CPU tradeoff
```

The README gives a concrete 48,000-sample / one-second-at-48-kHz comparison across internal SRAM, whole-object-in-SDRAM, external-buffer SDRAM, and internal-allocator SDRAM scenarios.

### Implementation highlights

- Provides `sdram_alloc.h/.cpp` bump allocator.
- Provides `delayline_ext.h` for externally supplied SDRAM buffers.
- Provides `delayline_sdram.h` for automatic SDRAM allocation.
- Example usage shows `hw.Init()`, `sdram_reset()`, external buffer allocation, and delay-line initialization.
- README benchmark compares four delay-line placement scenarios.
- For a single 48,000-sample delay line, reported SRAM drops from about 217 kB to about 25 kB when moving the buffer to SDRAM.
- Reported CPU load changes from 1.99% internal SRAM to about 2.19–2.26% in SDRAM cases.
- The README recommends external buffers for production-style modular code and internal allocation for drop-in simplicity.

### Hardware/electronics notes

No custom audio hardware. The hardware relevance is Daisy Seed’s external SDRAM and the practical memory budget for delay/reverb effects.

For module/pedal designs, this directly informs whether you can keep filters, UI buffers, and voice state in local SRAM while placing long audio history in SDRAM.

### Platform relevance

Daisy Seed, libDaisy, DaisySP delay lines, external SDRAM, long delay, reverbs, loopers, memory placement, real-time audio memory budgeting.

### Adaptation ideas

- Use the external-buffer version for multi-effect engines where several delay tanks share one memory pool.
- Reuse the benchmark table format when measuring Daisy Field/Seed delay, looper, and granular buffers.
- Compare SDRAM penalty against your expected reverb tank count before prematurely optimizing.
- Fold the allocator pattern into a static memory plan for Daisy Pod/Field experiments.
- Treat the WIP warning seriously and add bounds/stress tests before reuse.

### Quick engineering assessment

Correct lane: **REF_PASS**.

The repo is not a finished audio effect, but its value is high because memory placement is a recurring Daisy bottleneck. The measured tradeoff is more useful than most generic “use SDRAM” advice.

### Caveats / verification gaps

- The author marks the project experimental/WIP.
- The benchmark was not reproduced in this run.
- Source file paths beyond the README were not independently verified because connector file search did not expose them cleanly.
- Long-tail SDRAM/cache behavior should be measured under the actual reverb/looper workload, not only a one-delay-line benchmark.

## 5. glittershark / jazz granular engine — REF_PASS

Repository:

```text
https://github.com/glittershark/jazz
```

Granular source path:

```text
src/granular/granular.cpp
src/granular/granular.hpp
```

### Technical summary

`jazz` contains a Daisy Seed granular processing experiment with a custom buffer/update/head architecture. It is not well documented, but the source exposes a nontrivial implementation using read, write, and erase heads, random grain movement, fade handling, slab allocation, and a Daisy audio callback path.

### Why it matters

This is a hidden-gem reference, not a product candidate:

```text
circular sample buffer
+ scheduled write/erase updates
+ multiple moving heads
+ random grain jumps
+ fade state
+ fixed-capacity slab allocation
+ Daisy Seed callback wrapper
```

The most useful idea is the update-list model: buffer cells can temporarily carry pending write/erase updates, and housekeeping collapses them back into plain samples after fades complete. That is a different architecture from the common “grain objects read from a delay buffer” approach.

### Implementation highlights

- `BUFFER_LEN` is set to 22,050 samples, labelled as one second in the header.
- `MAX_FADE_TIME` is 128 samples.
- `NUM_HEADS` is 4.
- `Update` supports erase/write kinds with completion time, value, sample count, and next pointer.
- `IndicesToUpdate` uses a fixed-capacity slab list to schedule future housekeeping.
- `BufferValue` can represent either a plain sample or a sample with attached updates.
- Heads can be read/write/erase, move forwards/backwards, and optionally use random grain jumps with fade state.
- The non-unit-test build includes Daisy Seed headers, creates a `DaisySeed`, sets audio block size to 16, and starts an audio callback.
- The callback processes all heads per sample and outputs input plus the granular full-cycle output on output 0.

### Hardware/electronics notes

No custom electronics. The relevant hardware boundary is minimal Daisy Seed audio in/out. This is algorithm infrastructure only.

### Platform relevance

Daisy Seed, granular audio, custom allocation, callback-safe fixed-capacity data structures, delay-buffer mutation models, experimental DSP architecture.

### Adaptation ideas

- Study the scheduled update/housekeeping model for click-reduced erase/write operations in loopers.
- Replace `std::rand()` and dynamic/optional-heavy parts with deterministic callback-safe equivalents before production use.
- Port the buffer/head model into a test harness and compare against Clouds-style granular processing.
- Use the slab allocator idea for bounded real-time control/event queues.
- Treat this as a sketchpad for unusual looper/granular behavior rather than a ready module.

### Quick engineering assessment

Correct lane: **REF_PASS**.

This is ranked because the architecture is unusual and source-visible. It is not a buildable product and lacks README-level documentation, so it stays below the more complete items.

### Caveats / verification gaps

- No README was found through the connector.
- No compile/test run was performed.
- Some C++ constructs and random behavior need real-time review before audio-callback use.
- The “one second” comment for 22,050 samples depends on sample-rate assumptions and should not be treated as universal.
