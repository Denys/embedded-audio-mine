## Ranked entries

### 1) [t-dsp/t-dsp_desktop_pro + T-DSP ecosystem](https://github.com/t-dsp/t-dsp_desktop_pro) — **STRONG_PASS**

**Lane:** STRONG_PASS  
**Primary source:** https://github.com/t-dsp/t-dsp_desktop_pro  
**Related primary sources:**

- https://github.com/t-dsp/t-dsp_core
- https://github.com/t-dsp/t-dsp_tac5212_pro_audio_module
- https://github.com/t-dsp/t-dsp_software
- https://github.com/t-dsp/t-dsp_mic_array_module
- https://github.com/t-dsp/t-dsp_io_2x2_combo
- https://github.com/t-dsp/t-dsp_XLR_2x2

**Technical summary**

T-DSP is a modular desktop audio hardware ecosystem built around **Teensy 4.1** for real-time audio DSP, **ESP32** for UI/connectivity, and swappable audio modules/backplanes. The main promoted artifact is `t-dsp_desktop_pro`: a 120 mm × 100 mm desktop backplane with Teensy 4.1, ESP32, TAC5212 codec module, USB Audio, MIDI, S/PDIF, RCA I/O, headphone out, SD access, TDM expansion, and UI headers. The ecosystem also includes a lower-cost `t-dsp_core` 4-layer backplane and a standalone `t-dsp_tac5212_pro_audio_module` codec module.

**Why it matters**

This is the closest find today to the preferred **Polykit-style multi-repo hardware ecosystem**: reusable audio core, codec module, backplanes, expansion headers, software lane, and additional I/O/mic modules. It is not only a single instrument or carrier board; it is a platform architecture that could be adapted into synths, desktop effects, loopers, mixers, audio tools, or custom performance boxes.

**Implementation highlights**

- Teensy 4.1 runs real-time DSP via Teensy Audio Library.
- ESP32 handles UI, WiFi/Bluetooth, display/buttons/encoder, and serial command path to Teensy.
- TAC5212 module provides stereo ADC/DAC and codec control over I²S/I²C.
- Desktop Pro exposes RCA stereo input/output, headphone output, S/PDIF I/O, USB-C device, USB-A host, TRS MIDI input with optical isolation, MIDI GPIO, SD access, OLED/TFT/SK6812 UI headers, and TDM expansion.
- T-DSP Core provides a smaller 4-layer variant with USB Audio, MIDI, Ethernet, and TDM expansion.
- TAC5212 module is designed as a chip-on-board module with 52-pin headers and KiCad footprint support.

**Hardware / electronics notes**

- Desktop Pro claims an **8-layer PCB** with ground/power planes, clean analog regulation, and separated analog/digital ground domains.
- T-DSP Core claims a **4-layer PCB** with analog/digital domains and expansion headers.
- TAC5212 module supports line, instrument, and dynamic mic use cases; programmable input impedance; DC-coupled input option; headphone/line/balanced-style output use cases; TVS protection; ferrite input filtering; LDO regulation; buffered digital outputs.
- Expansion architecture is useful: TDM digital bus, I²C control, power rails, held-high/held-low control pins, and multi-module chaining.

**Hardware modifiability**

- **Editable CAD/source:** README-verified KiCad project files and custom KiCad libraries.
- **Schematic:** README links schematic PDF and KiCanvas schematic; connector fetch of `.kicad_sch` returned empty text in this run, so schematic internals were not parsed.
- **PCB source:** README links KiCanvas PCB; connector fetch of `.kicad_pcb` returned empty text in this run, so layout internals were not parsed.
- **Manufacturing artifacts:** README-verified manufacturing outputs, Gerbers/BOM/CPL/iBOM flow; TAC5212 module explicitly documents KiBot-generated Gerbers, JLCPCB BOM, generic BOM, CPL, schematic PDF, PCB PDF, and iBOM.
- **Enclosure/panel:** 3D renders, 3D models, panels, and rendered docs are present by README; mechanical source depth not fully inspected.
- **License:** CC BY-NC-SA 4.0, which is useful for learning/adaptation but restricts commercial use.

**Platform relevance**

Very high for custom desktop embedded-audio hardware. This is directly relevant to Teensy 4.1 audio products, custom codec front ends, UI/audio split architectures, TDM expansion, and modular hardware families.

**Adaptation ideas**

- Use Desktop Pro/Core as reference for a **custom desktop synth/effects backplane**: Teensy DSP + ESP32 UI + codec/audio module + MIDI/USB.
- Adapt the TAC5212 module idea into a reusable **codec mezzanine** for Daisy/STM32H7/RP2350 experiments.
- Study TDM expansion bus design for multi-module instruments: voice cards, FX cards, CV/audio I/O, sampler storage boards.
- Use the ESP32/Teensy split as a pattern for keeping UI/networking away from audio callback timing.

**Quick engineering assessment**

High-value architecture. The platform is more product-like than most hobby synth repos: power, ESD, reverse polarity, codec front-end, audio I/O, UI, manufacturing, and expansion are all in scope. The main caveat is maturity: README says active development, and the TAC5212 module notes that the current revision has not yet been built, though a previous board was functional and issues were addressed.

**Caveats / verification gaps**

- Non-commercial license limits direct commercial reuse.
- Connector could not parse schematic/PCB source text for Desktop Pro in this run despite README links; therefore internal net/layout quality remains unverified.
- Current TAC5212 module revision is not yet built according to README; treat as strong design reference, not proven production hardware.
- Need future pass on `t-dsp_software` to judge firmware/application maturity.

**Sources**

- https://github.com/t-dsp/t-dsp_desktop_pro
- https://github.com/t-dsp/t-dsp_core
- https://github.com/t-dsp/t-dsp_tac5212_pro_audio_module
- https://github.com/orgs/t-dsp/repositories

### 2) [polpo/picogus](https://github.com/polpo/picogus) — **PASS**

**Lane:** PASS  
**Primary source:** https://github.com/polpo/picogus

**Technical summary**

PicoGUS is an RP2040/Pico-based ISA sound-card and CD-ROM emulation project. It can emulate Gravis Ultrasound, Sound Blaster 16 / Sound Blaster Pro 2 / AdLib OPL, MPU-401 intelligent mode with MIDI output on a 3.5 mm TRS connector, Tandy 3-voice, CMS/Game Blaster, game-port joystick, and Panasonic/MKE CD-ROM interface.

**Why it matters**

It is not a synth workstation, but it is a serious embedded-audio hardware/software system with hard compatibility constraints, real hardware distribution, source hardware licensing, and a deep firmware stack. For embedded audio design, it is valuable as a reference for **low-level audio emulation, bus timing, MIDI routing, I²S audio, compatibility testing, and constrained RP2040 DSP/audio tradeoffs**.

**Implementation highlights**

- RP2040/Pico core with ISA bus-facing audio/emulation behavior.
- Multiple emulated sound devices: GUS, SB/AdLib OPL, MPU-401, Tandy, CMS/Game Blaster.
- MIDI output through 3.5 mm TRS for MPU-401 use.
- Firmware derives/credits substantial emulation blocks from DOSBox-X, HardMPU, rp2040-doom/emu8950, DREAMM, Pico SDK, pico_audio_i2s, TinyUSB, and FatFS.
- Existing assembled PicoGUS 2.0 cards are sold by multiple shops; DIY build guide exists.

**Hardware / electronics notes**

- KiCad schematic under `hw/` is present and parsed as PicoGUS rev v1.2.
- Hardware includes ISA-bus interfacing logic; parsed schematic content includes 74FST3257DR2G bus-switch/mux-style component properties.
- README explicitly separates hardware and software licensing and references build/configuration guides.

**Hardware modifiability**

- **Editable CAD/source:** KiCad schematic verified. PCB path exists, but connector returned empty content for `.kicad_pcb` in this run, so PCB internals were not parsed.
- **Schematic:** present and parsed.
- **PCB source:** path verified but content not parsed here.
- **Build docs:** README links build guide and configuration guide.
- **License:** hardware under CERN-OHL-P v2; software collection GPLv2 with some BSD/MIT files.
- **Fabrication maturity:** assembled v2.0 cards are available, but DIY v1.1.1 has documented reset issues and the project remains “perpetual beta.”

**Platform relevance**

High for retro/digital embedded audio, less direct for modern standalone synth hardware. The RP2040 + compatibility-emulation angle is valuable: exact bus behavior, MIDI output, audio emulation, USB/mass-storage support, and legacy system integration are strong references.

**Adaptation ideas**

- Extract RP2040 audio-emulation patterns for a **retro wavetable/FM module** or educational sound-card emulator.
- Reuse MPU-401/MIDI routing concepts in a standalone MIDI utility or hardware sequencer.
- Study timing/compatibility caveats for RP2040 real-time audio under hostile external bus conditions.
- Use as a reference for documentation style around compatibility lists, beta caveats, and build guides.

**Quick engineering assessment**

Technically impressive and unusually complete. It is not ranked above T-DSP because it is a retro PC expansion card, not a self-contained synth/audio product platform. Still, the hardware/source/license evidence is stronger than many “synth” repos.

**Caveats / verification gaps**

- Non-standalone in normal music-hardware sense; it lives inside/with an ISA retro PC.
- Current status is explicitly beta.
- Connector did not parse PCB layout text, only schematic/source path evidence.
- Some DIY hardware versions have documented reset issues.

**Sources**

- https://github.com/polpo/picogus
- https://github.com/polpo/picogus/wiki

### 3) [thenfour/Clarinoid](https://github.com/thenfour/Clarinoid) — **PASS**

**Lane:** PASS  
**Primary source:** https://github.com/thenfour/Clarinoid

**Technical summary**

`thenfour/Clarinoid` is a large Teensy-oriented custom instrument/hardware ecosystem. The most convincing evidence in this pass came from the **BOMMANOID** branch of the repo: multiple KiCad CAD iterations, RC1 hardware notes, PlatformIO Teensy 4.1 firmware, OLED/display handling, USB host MIDI, MIDI, Teensy Audio, encoders, WS2812 LEDs, and internal crash/memory profiling notes.

**Why it matters**

This is the “messy but real product iteration” type of source that is often more useful than polished one-file synth demos. It appears to contain several generations of custom instrument hardware, not just a PCB render. For adaptation, the value is in the physical control-surface + firmware architecture + CAD iteration history.

**Implementation highlights**

- PlatformIO target for Teensy 4.1 / `teensymm`, Arduino framework, C++17 build flags, USB_MIDI_SERIAL.
- Firmware includes USBHost_t36, MIDI, Audio, Encoder, WS2812Serial, SSD1306 display, SPI/Wire, and a `BommanoidApp` main loop.
- Development notes discuss Teensy crash handling, address-to-line debugging, RAM1 pressure, bloaty memory analysis, and C++ toolchain caveats.
- CAD/BOM notes document multiple hardware revisions from sketches through routing, peripheral breakouts, RC1, FX loop, suspended castellated subboard, panelization, ERC/DRC notes, and JLCPCB order separation.

**Hardware / electronics notes**

- Many KiCad project/schematic/PCB/BOM/CSV paths were found under `CAD/bommanoid` and related directories.
- BOMMANOID CAD notes mention RC1, FX loop, suspended castellated subboard, peripheral breakouts, and ERC/DRC status.
- The actual hardware/electronics architecture is not summarized cleanly in a top README, so deeper local checkout would be required before fabrication decisions.

**Hardware modifiability**

- **Editable CAD/source:** multiple KiCad `.kicad_pro`, `.kicad_sch`, `.kicad_pcb`, CSV/BOM-style paths visible.
- **Schematic:** multiple schematic paths visible; representative CAD notes read.
- **PCB source:** multiple PCB/project paths visible; not deeply parsed.
- **Firmware source:** PlatformIO Teensy 4.1 project and main source verified.
- **Build path:** PlatformIO project verified.
- **License:** not verified; no root license found in this run.
- **Documentation:** fragmented; no root README found.

**Platform relevance**

High if the goal is standalone custom instrument hardware with dense UI. It is relevant to Teensy 4.1 synths, wind/controller-like instruments, custom control surfaces, USB host MIDI, OLED UI, and memory-stressed embedded audio firmware.

**Adaptation ideas**

- Mine CAD history for custom handheld/desktop synth enclosure and control-board patterns.
- Extract Teensy crash/memory profiling practices into future audio firmware workflow.
- Study the OLED/encoder/MIDI/USB-host architecture for custom performance controllers.
- Use BOMMANOID CAD evolution as a cautionary reference for board iteration and panelization.

**Quick engineering assessment**

Promoted for uniqueness and depth, not polish. This is a strong engineering mine, but not immediately buildable from a clean README. It should be treated as a source-hardware/firmware archaeology target before any serious reuse.

**Caveats / verification gaps**

- No root README found.
- No license verified.
- Project structure is large and fragmented; exact final hardware target needs deeper checkout.
- Build was not run; CAD was not opened visually.

**Sources**

- https://github.com/thenfour/Clarinoid
