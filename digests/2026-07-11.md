### 1) [brer-rabbit/zoxnoxious](https://github.com/brer-rabbit/zoxnoxious) — **STRONG_PASS**

#### Technical summary

Zoxnoxious is a modular analog synthesizer platform built around reusable **Z-Cards**, a six-slot backplane and a Raspberry Pi Zero 2 controller. The Pi presents USB Audio and USB MIDI to a host computer, then routes control over SPI/I²C to individual cards. A VCV Rack plugin provides the intended high-level patching and control interface.

The hardware family is unusually broad rather than a cosmetic set of variations:

- **Z3340:** AS3340 VCO with four combinable sync modes.
- **Z3372:** AS3372 low-pass filter/VCA with stereo panning and modulation.
- **Z5524:** SSI2130 through-zero-FM oscillator plus AS3394 second VCO, VCF and VCA.
- **Pole Dancer:** SSI2140/SSI2190 pole-mixing multimode filter.
- **Z2203:** YM2203-based FM voice card.
- **Development template:** standard card mechanics plus DAC, GPIO expander and starter layout.

#### Why it matters

This is the closest new find to the preferred **Polykit ecosystem archetype**, but with a stronger explicit expansion bus. The value is not merely the individual synth circuits: it is the partitioning of analog voice electronics, digital control, physical card format and host software into replaceable layers. That supports product families, test fixtures and derivative voice/effect cards without redesigning the complete instrument.

#### Implementation highlights

- Six physical card slots with a defined addressed signal/control bus.
- Pi Zero 2 control layer exposing USB Audio and USB MIDI.
- SPI/I²C card-driver abstraction rather than hard-wiring one controller to one analog voice.
- VCV Rack plugins that map host controls and CV-style routing to the hardware cards.
- Demonstrated Z3340 and Z5524 boards, including hardware-detail and autotune material.
- Active code/UI correction history around the Z5524 control and visualisation path.

#### Hardware and electronics notes

**Hardware modifiability:**

- Editable KiCad project and schematic files: **verified**.
- PCB source paths: **verified**, but the connector did not parse the large PCB payload internally.
- Backplane source: **advertised and repository-present**.
- Front-panel source: **repository-present**.
- Card-development template: **verified**, including DAC/GPIO-expander schematic material.
- Assembly information: **present for the hardware family**.
- Card-specific datasheets: **partial**; the Z5524 README still marks its datasheet TBD.
- Licence: root **GPLv3** verified; this is less precise for hardware reuse than CERN-OHL or a clearly scoped Creative Commons hardware licence.

The SSI2130 + AS3394 Z5524 card is particularly valuable. It combines TZFM, conventional VCO functions, waveshape modulation, sync variants, VCF and VCA on a reusable voice card. The Z3340 and Z3372 cards offer simpler decomposed alternatives, making the repository useful for both integrated and modular product directions.

#### Platform relevance

- **High:** standalone/semi-modular analog synth architecture.
- **High:** reusable analog voice-card ecosystem.
- **High:** mixed Linux/embedded/analog product partitioning.
- **Medium:** direct pedal/audio-effect reuse.
- **Medium:** manufacturing readiness; source depth is good, but per-card production package consistency needs a local checkout audit.

#### Adaptation ideas

1. Replace the Pi/VCV-dependent host with an STM32H7 or RP2350 controller, local display and physical UI for a fully standalone instrument.
2. Productise one Z5524 or Z3340/Z3372 combination as a desktop semi-modular voice with MIDI, CV/gate and patch memory.
3. Retain the Z-Card electrical/mechanical standard but add digital DSP, codec, effects and sampler cards.
4. Extract the card ABI, autotune path and driver/plugin abstraction into a reusable multi-voice test platform.
5. Add card identity EEPROMs and calibration storage so a controller can discover and configure mixed card sets automatically.

#### Quick engineering assessment

**Promote.** The platform is architecturally differentiated, source-modifiable and directly aligned with multi-board synth product development. The principal engineering task is not proving the concept; it is reducing dependence on the VCV/Pi host, defining a cleaner commercial hardware licence, and auditing power/signal-bus margins across mixed cards.

#### Caveats and verification gaps

- Intended operation is strongly coupled to Raspberry Pi and VCV Rack; standalone local UI is not the current centre of gravity.
- GPLv3 exists, but hardware-file licensing scope is not explicitly separated.
- Large `.kicad_pcb` contents were not parsed in this run, although project and PCB paths were verified.
- A unified BOM, release package and manufacturing checklist were not verified for every card.
- Some documentation remains card-specific and uneven.

### 2) [SloBloLabs/LivSynth](https://github.com/SloBloLabs/LivSynth) — **STRONG_PASS**

#### Technical summary

LivSynth is a complete standalone hybrid instrument centred on an **STM32F405**, an analog synth signal path, a dense local control surface, USB MIDI/CDC, sequencing and onboard audio output. Unlike many attractive but incomplete repositories, it contains the firmware project, CubeMX configuration, GNU ARM/CMake build flow, editable KiCad hardware, faceplate material, iBOM setup, DFU instructions and staged assembly/calibration guidance.

#### Why it matters

LivSynth is a credible example of how to package analog synthesis, digital control, sequencing, USB and user interface electronics on a self-contained product. The README is not a polished product specification, but its practical build instructions expose the less glamorous details that make the design useful: staged power bring-up, matched transistors, tempco handling, panel alignment, speaker integration, DFU recovery and VCO calibration.

#### Implementation highlights

- STM32F405 firmware with CubeMX `.ioc`, CMake/GNU ARM toolchain and OpenOCD support.
- Composite USB device with two CDC interfaces plus MIDI.
- Incoming MIDI note handling and sequencer-step capture in the v0.2.5 change history.
- Exact DFU flashing path and a documented successful transfer flow.
- Integrated control surface, illuminated controls, onboard speaker and battery-holder accommodation.
- Smoke-test and analog calibration sequence for VCO amplitude, waveform bias and tracking.

#### Hardware and electronics notes

**Hardware modifiability:**

- Editable KiCad mainboard project/schematic: **verified**.
- Editable faceplate KiCad project: **verified**.
- PCB source path: **verified**, but the connector returned an empty payload when attempting internal parsing.
- iBOM configuration: **verified**.
- Assembly procedure: **verified and unusually detailed**.
- Calibration/test notes: **verified**.
- Firmware and build files: **verified**.
- Licence: root MIT licence **verified**, though it describes “Software” and does not explicitly clarify hardware-file scope.

The assembly instructions call out matched transistor pairs, tempco components and analog calibration. This is strong evidence that the design is not merely an MCU audio sketch with decorative analog circuitry. The USB composite implementation is also reusable for product servicing: one interface can support control/debug while MIDI remains available to the instrument.

#### Platform relevance

- **High:** standalone hybrid synthesizer and control-surface design.
- **High:** analog calibration and production bring-up reference.
- **High:** STM32 USB MIDI/CDC architecture.
- **Medium:** direct reuse, because STM32F405 and some peripheral choices are now dated.
- **Medium:** commercial adaptation, pending hardware-licence clarification.

#### Adaptation ideas

1. Re-spin the controller around STM32G4/H7 while retaining the analog voice and panel concept.
2. Split the analog voice, controller/UI and power sections into serviceable boards rather than one dense mainboard.
3. Add precision DAC/ADC feedback for automated V/oct calibration and stored compensation curves.
4. Upgrade power and connectivity to USB-C, protected TRS/DIN MIDI and a cleaner low-noise analog rail strategy.
5. Reuse the composite CDC+MIDI firmware pattern for bootloader, diagnostics, editor and field calibration.

#### Quick engineering assessment

**Promote.** LivSynth is less novel than Zoxnoxious as an ecosystem, but it is more immediately instructive as a finished instrument. A local KiCad/ERC/DRC and BOM audit is required before fabrication, and a modern derivative should retain the analog/mechanical lessons while replacing ageing digital and power choices.

#### Caveats and verification gaps

- STM32F405 and the 2022-era hardware revision are not the preferred foundation for a new premium design.
- Feature documentation is distributed between videos, source and build notes rather than one coherent hardware specification.
- PCB internals and full BOM were not parsed in this run.
- The root MIT licence does not explicitly state whether hardware CAD is covered.
- Long-term component availability and EMC behaviour were not evaluated.

### 3) [shmoergh/hog](https://github.com/shmoergh/hog) — **PASS**

#### Technical summary

Hog rev. 3 is a standalone, fully analog, two-voice monophonic performance synth built from five separate boards. Its embedded portion is a Raspberry Pi Pico MIDI-to-CV board using a 6N138 MIDI input, MCP4822 dual DAC and analog conditioning. The remaining system covers power, stable and experimental core variants, user interface, output and a Steiner-Parker VCF.

#### Why it matters

Hog is one of the best fabrication and product-partitioning references in this pass. It has editable KiCad projects, a full Mouser BOM, per-board Gerbers, JLCPCB assembly files for SMD-heavy boards, panel/control integration and a real build guide. It is ranked below LivSynth because the embedded/DSP content is limited and its licence terms materially restrict product adaptation.

#### Implementation highlights

- Five-board architecture instead of a monolithic PCB.
- Separate stable and experimental core variants.
- RP2040/Pico MIDI-to-CV section with optoisolated MIDI input and dual precision DAC.
- Dedicated PSU, UI and Steiner-Parker VCF boards.
- Consolidated Mouser BOM with vendor part numbers and per-board references.
- JLCPCB BOM/position files for the Core and Filter boards.
- Explicit submodule/build instructions for the MIDI-to-CV firmware.

#### Hardware and electronics notes

**Hardware modifiability:**

- Editable KiCad projects: **verified** for UI, PSU, stable/experimental Core, MIDI2CV and VCF.
- PCB source: **repository-present**.
- Schematics: **repository-present**.
- BOM: **verified**, including a consolidated Mouser list.
- Gerbers and JLC placement data: **verified by repository documentation**.
- Assembly/build guide: **verified**.
- Firmware: **verified through the Pico MIDI2CV submodule path**.
- Hardware licence: **CC BY-NC 4.0**.
- Software licence: **MIT**.

The MIDI2CV BOM is a clean reusable subsystem: 6N138 isolation, MCP4822 DAC, LM358 conditioning and RP2040/Pico control. The broader analog core uses matched devices, tempco elements and trimmers, making it relevant to manufacturability and calibration studies even when the exact synth voice is not reused.

#### Platform relevance

- **High:** standalone analog synth construction and mechanical partitioning.
- **High:** BOM/manufacturing-document discipline.
- **Medium:** embedded MIDI-to-CV reference.
- **Low-to-medium:** DSP/codec architecture.
- **Low:** direct commercial derivative, because the hardware licence is non-commercial and the README also states private-use-only conditions.

#### Adaptation ideas

1. Reimplement the MIDI-to-CV subsystem with a commercially clean schematic and modern low-offset output stages.
2. Reuse the five-board partitioning as a serviceable analog/digital instrument chassis architecture.
3. Add digitally controlled calibration, preset storage and patch recall while preserving the analog path.
4. Derive a safe low-voltage desktop instrument with separately replaceable voice and filter boards.
5. Use the stable/experimental board split as a formal production-versus-R&D hardware workflow.

#### Quick engineering assessment

**Reference and redesign, not direct product fork.** The source and manufacturing package are strong enough to learn from and privately prototype. A commercial project should independently redraw the valuable circuits and mechanics under a clean licence rather than trying to interpret the repository’s NC/private-use wording permissively.

#### Caveats and verification gaps

- CC BY-NC and “private use only” language block straightforward commercial exploitation.
- Analog-heavy architecture offers less reusable embedded-audio DSP value than the first two entries.
- Safety disclaimer is broad and mentions potentially lethal voltages; the actual product-power implementation still requires independent review.
- No production validation, emissions/immunity or reliability evidence was verified.
