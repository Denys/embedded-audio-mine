### 1) [`ctag-fh-kiel/ctag-tbd`](https://github.com/ctag-fh-kiel/ctag-tbd) — **STRONG_PASS**

**Technical summary:** ESP32-based open-source Eurorack audio processing platform with 50+ audio generators/effects, plugin architecture, sample ROM playback, wavetable oscillator support, wireless browser UI, REST API, simulator, cloud compiler, GitHub Action build path, and release binaries flashable through module web UI or serial tools.

**Why it matters:** This is a full embedded audio platform rather than a small demo. It combines firmware, plugin architecture, hardware target, web UI, REST control, simulator, release workflow, sample ROM tooling, and constrained ESP32 optimization.

**Implementation highlights:**

- ESP32 Eurorack firmware with plugin-based sound processors.
- More than 50 generators/effects.
- Sample ROM playback and user wavetable flow.
- Web UI and REST API.
- Simulator for plugin development without hardware.
- Cloud compiler for plugin-subset firmware builds.
- v1.0.0 work includes newer Mutable Instruments codebase use, TBDaits/Plaits model coverage, dual oscillator plugins, TBD-BBA hardware support, MIDI improvements, custom allocator, ESP-IDF 5.5, LittleFS migration, backup/restore fixes, and plugin bug fixes.

**Platform relevance:** ESP32, Eurorack DSP, browser-controlled embedded instruments, plugin firmware architecture, sample ROMs, wavetable engines, simulator-backed audio development.

**Adaptation ideas:**

- Study the plugin architecture as an ESP32-side equivalent to Daisy multi-app frameworks.
- Treat the web UI + REST API as a model for headless Eurorack modules.
- Mine the simulator path for faster DSP iteration before hardware flashing.
- Compare ESP32 constraints against Daisy/Teensy/RP2350 for plugin count and UI latency.

**Quick engineering assessment:** Best item today. CPU headroom is not Daisy/Teensy-class, but the system architecture is unusually complete and worth studying.

**Sources:** [repo](https://github.com/ctag-fh-kiel/ctag-tbd), [components](https://github.com/ctag-fh-kiel/ctag-tbd/tree/master/components), [simulator](https://github.com/ctag-fh-kiel/ctag-tbd/tree/master/simulator)

### 2) [`CarlosDerSeher/snapclient`](https://github.com/CarlosDerSeher/snapclient) — **STRONG_PASS**

**Technical summary:** ESP32 Snapcast client for synchronous multiroom audio streaming. It supports FLAC, OPUS, and PCM decoding; Wi-Fi provisioning; Snapcast server auto-discovery; I2S DAC output; sync buffering; DSP/EQ processing; HTTP-side control work; OTA update flow; and ESP-IDF v5.x builds.

**Why it matters:** Not a synth, but highly relevant embedded audio infrastructure. Codec decode, jitter/playback buffering, timestamped sync, I2S DMA, OTA update, board abstraction, and DSP/EQ are reusable in distributed instruments, synchronized speaker nodes, and headless audio boxes.

**Implementation highlights:**

- Snapcast client port for ESP32 / ESP32-S2 class hardware.
- FLAC, OPUS, and PCM 16-bit stream support.
- Custom sync backend using server timestamps, playback-delay compensation, jitter buffering, and I2S DMA output.
- Board/DAC configuration paths for common ESP audio boards and I2S DAC/class-D parts.
- DSP flow options include stereo, bass boost, bi-amp, bass/treble EQ, and optimized ESP32 biquad options.

**Platform relevance:** ESP32, ESP-IDF, I2S DACs/class-D amps, networked audio, synchronized playback, OTA update, Wi-Fi provisioning, HTTP control.

**Adaptation ideas:**

- Use the sync queue/backend split as a reference for distributed synth nodes.
- Borrow the board/DAC abstraction for ESP32 audio product experiments.
- Reuse OTA + HTTP UI patterns in headless pedal/module firmware.
- Compare the sync model against RTP-MIDI clocking and Linux SBC Snapcast clients.

**Quick engineering assessment:** Strong infrastructure pick. The codebase is not tiny and likely has refactoring debt, but it addresses real embedded audio system problems missing from most synth demos.

**Sources:** [repo](https://github.com/CarlosDerSeher/snapclient)

### 3) [`ohmtech-rdi/eurorack-blocks`](https://github.com/ohmtech-rdi/eurorack-blocks) — **REF_PASS**

**Technical summary:** Daisy Patch Submodule-oriented Eurorack development framework. It lets a developer describe module UI/hardware blocks, write DSP in C++/Faust/Max, test in a virtual Eurorack environment, and generate Daisy firmware build files plus manufacturing outputs such as panel drawings, Gerbers, KiCad PCB, BOM, and print/milling files.

**Why it matters:** The value is workflow architecture: DSP idea → virtual Eurorack test → generated firmware/hardware artifacts → physical Daisy-based module. That is directly useful for turning one-off embedded audio sketches into repeatable modules.

**Implementation highlights:**

- Targets Daisy Patch Submodule.
- Supports C++, Faust, and Cycling '74 Max workflows.
- Generates simulator artifacts and Daisy firmware build files.
- Generates hardware outputs: BOM CSV, DXF/panel files, Gerbers, KiCad PCB, and panel artwork.
- Includes sample modules such as bypass, drop, reverb, kick, Faust, custom, and Frohmager-style filter examples.

**Platform relevance:** Daisy Patch Submodule, Eurorack module development, VCV Rack simulation, C++/Faust/Max DSP, PCB/panel generation, hardware/software co-design automation.

**Adaptation ideas:**

- Use it as a model for a Daisy module generator workflow.
- Compare its declarative UI format with diagram-driven documentation workflows.
- Reuse the simulator-first model for custom Daisy Field/Pod hardware.
- Study the limits of generated hardware files before trusting them for manufacturable mixed-signal boards.

**Quick engineering assessment:** Correct lane is REF_PASS. It is not a single flashable instrument, but it is one of the best workflow references for moving from DSP code to physical Eurorack hardware.

**Sources:** [repo](https://github.com/ohmtech-rdi/eurorack-blocks), [README](https://github.com/ohmtech-rdi/eurorack-blocks/blob/main/README.md), [manifest](https://github.com/ohmtech-rdi/eurorack-blocks/blob/main/manifest.md)

### 4) [`h4yn0nnym0u5e/AudioPatcher`](https://github.com/h4yn0nnym0u5e/AudioPatcher) — **REF_PASS**

**Technical summary:** Teensy runtime-configurable synthesizer / audio graph experiment based on the dynamic Teensy Audio library. It exposes audio objects, patchcord editing, parameter editing, MIDI editing, delete/file modes, SD-card patch loading, display drawing of audio objects/patchcords, M5Stack control modules, SGTL5000/I2S I/O, CPU/heap status display, and a broad Teensy Audio object palette.

**Why it matters:** The interesting idea is runtime patching on Teensy. It pushes beyond static Audio Design Tool graphs toward an embedded modular patcher where routing and object parameters can change without recompilation.

**Implementation highlights:**

- Maintains vectors of audio object instances and patchcord instances.
- UI modes include objects, patchcords, parameter editing, MIDI config, deleting, and filing.
- SD-card patch loading is present, with startup logic avoiding reload after crash.
- CPU max, free heap, sounding voices, and releasing voices can be shown on display.
- Object list includes analysis, effects, filters, mixers, synths, wavetable, Dexed, granular, wavefolder, Freeverb, state-variable filter, ladder filter, delay, and more.

**Platform relevance:** Teensy 4.x, Teensy Audio, dynamic audio graphs, embedded modular synth UI, patch storage, MIDI mapping, display/control surface design.

**Adaptation ideas:**

- Use as a source-level reference for a small-screen modular graph editor.
- Extract the object/cord/parameter/MIDI/file mode split for Daisy Field UI planning.
- Compare dynamic graph cost/fragility against fixed compile-time audio graphs.
- Study crash-aware patch loading before implementing persistent patch recall.

**Quick engineering assessment:** REF_PASS, not PASS. No polished top-level docs and likely rough build assumptions, but the runtime graph idea is real and valuable as architecture research.

**Sources:** [repo](https://github.com/h4yn0nnym0u5e/AudioPatcher), [AudioPatcher.ino](https://github.com/h4yn0nnym0u5e/AudioPatcher/blob/trunk/AudioPatcher/AudioPatcher.ino), [objects.h](https://github.com/h4yn0nnym0u5e/AudioPatcher/blob/trunk/AudioPatcher/objects.h)

### 5) [`marcel-licence/ML_SynthTools`](https://github.com/marcel-licence/ML_SynthTools) — **REF_PASS**

**Technical summary:** Cross-platform Arduino synthesizer toolkit with modules for MIDI input, arpeggiator, board definitions, delay, reverb, organ generator, saw/square PWM oscillator, VU meter, OLED scope, MIDI-file stream playback, and MOD tracker playback. It targets ESP32 variants, ESP8266, Seeed XIAO/SAMD21, Teensy 4.1, Daisy Seed, RP2040, RP2350, STM32F3, and STM32F407.

**Why it matters:** The value is portability. It attempts to normalize synth/audio building blocks across nearly every low-cost MCU family relevant to embedded audio experimentation.

**Implementation highlights:**

- Multi-platform Arduino-style synth library.
- Platform support spans ESP32 variants, ESP8266, SAMD21, Teensy 4.1, Daisy Seed, RP2040, RP2350, STM32F3, and STM32F407.
- Modules include MIDI, arpeggiator, delay, reverb, organ, oscillator, VU meter, OLED scope, MIDI file stream, and MOD tracker.
- Example projects include e-piano, basic synth, multi-saw/supersaw, full-polyphony organ, PWM oscillator, and MOD tracker.
- README includes a specific ESP32 board-library compatibility warning around Serial1/Serial2.

**Platform relevance:** ESP32, Teensy 4.1, Daisy Seed, RP2040/RP2350, STM32, Arduino-Pico, cross-platform synth middleware, MIDI utilities, embedded instrument scaffolding.

**Adaptation ideas:**

- Use as a cross-platform sanity baseline before choosing Daisy vs Pico 2 vs ESP32.
- Compare its oscillator/effect abstractions against DaisySP and Teensy Audio objects.
- Mine board-definition patterns for a portable synth tutorial or test harness.
- Use MOD tracker and MIDI file stream components as lightweight embedded playback references.

**Quick engineering assessment:** REF_PASS because it is broad and library-like, not a focused finished instrument. Still useful because platform portability is a real embedded audio pain point.

**Sources:** [repo](https://github.com/marcel-licence/ML_SynthTools)
