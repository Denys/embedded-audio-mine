## Ranked entries

### 1) [yottanami/yottasynth](https://github.com/yottanami/yottasynth) — **PASS**

**Lane:** standalone touchscreen synthesizer / performance instrument.

**Technical summary:** Yottasynth is an active Teensy 4.1 mono-synth instrument with a 2.8-inch-class ILI9341/XPT2046 touch interface, five context-sensitive physical knobs, USB-host MIDI input, arpeggiator, 16-step sequencer, and selectable Persian/Iranian tuning tables. The audio engine uses the Teensy Audio ecosystem and an SGTL5000 I2S codec path. Its current effects are echo, reverb, and drive.

**Why it matters:** This is not merely a synth sketch or generic development-board carrier. It joins editable hardware, a coherent panel/UI model, playable firmware, culturally specific musical functionality, and current development activity. The page-plus-five-knob interaction model is particularly reusable for compact desktop synths and pedals where control depth must be preserved without a knob-per-function panel.

**Implementation highlights:**

- Teensy 4.1 target under PlatformIO/Arduino.
- LVGL UI with TFT_eSPI and XPT2046 touch support.
- USB host MIDI performance input.
- Five physical controls scanned through a 74HC4067 multiplexer, plus a confirmation control.
- Mono voice with two oscillators, noise, state-variable filtering, envelope, glide, LFO, and pitch-bend support.
- Shared transport for arpeggiator and 16-step sequencer.
- Echo using delay/feedback mixers, Freeverb path, and drive combining waveshaping and bit crushing.
- SGTL5000 control plus I2S stereo output.
- Diagnostic/input-test page covering touch, controls, MIDI, and audio status.
- Recent repository work includes tuning additions, effects, waveform control, sequencer/touch fixes, and generated UI documentation.

**Hardware/electronics notes:**

- `etc/board/board.kicad_sch` was directly parsed as a KiCad 8 schematic.
- `etc/board/board.kicad_pcb` was directly parsed as a KiCad 8 two-layer PCB with Gerber output configuration.
- `platformio.ini` directly identifies the Teensy 4.1 target and UI libraries.
- `src/audio_setup.cpp` directly identifies `AudioControlSGTL5000`, I2S output, oscillators, mixers, filters, envelopes, delay, reverb, waveshaper, and bitcrusher objects.
- No standalone generated BOM, assembly package, or enclosure CAD was verified.
- Current developer documentation warns that the board documents may reflect an older multiplexer wiring arrangement; active firmware mapping is the source of truth. This is a meaningful design-control issue, not a cosmetic documentation gap.

**Hardware modifiability:** editable KiCad schematic present; editable KiCad PCB present; project files present; Gerber generation configured; firmware source and build manifest present; BOM not separately verified; enclosure/panel CAD not verified; license not verified.

**Platform relevance:** high for Teensy-based desktop synths and compact multi-function pedals. The control/UI pattern is more valuable than the mono engine itself: five soft-assigned knobs plus touch pages can scale to deeper effects or multi-engine instruments without overwhelming a novice panel.

**Adaptation ideas:**

- Replace the current custom board/audio-shield arrangement with an integrated Teensy 4.1 + codec board using a modern codec and explicit line/instrument I/O.
- Reuse the page/five-knob control model for the separate multi-FX pedal concept, with simple mode names but deep secondary pages.
- Add preset storage, MIDI DIN/TRS, clock input, and a dedicated bypass/performance control layer.
- Retain the alternate-tuning architecture and generalize it to Scala/MTS-style tables.
- Split UI/control from audio updates more rigorously if the synth becomes polyphonic or the effects graph becomes heavier.

**Quick engineering assessment:** the most useful new standalone-instrument reference today. Source depth is sufficient for architectural mining and hardware modification, but the missing license and the documented hardware/firmware mapping drift prevent `STRONG_PASS`.

**Caveats / verification gaps:**

- No LICENSE file was found; the README says open hardware, but reuse terms remain legally unclear.
- The repository describes the project as active work in progress.
- Board-versus-firmware multiplexer mapping is not fully synchronized.
- No automated firmware tests are present.
- BOM, assembly documentation, EMC/power validation, noise floor, latency, and production history were not verified.

**Sources:**

### 2) [mod-audio/hw-mod-dwarf](https://github.com/mod-audio/hw-mod-dwarf) — **PASS**

**Lane:** standalone Linux audio processor / multi-effects pedal product-hardware reference.

**Technical summary:** This repository contains the source-hardware package for the MOD Dwarf. The main-board design is partitioned into hierarchical power, core-board, CS4265 codec, audio-input, audio-output, headphone, USB, MIDI, control-chain, and mechanics sheets. A separate controller-board Altium project and a large grouped BOM are also present.

**Why it matters:** MOD Dwarf provides something most hobby repositories do not: the electronics structure of a real product-scale audio processor. It is valuable for studying partitioning, serviceable board boundaries, codec/I2S integration, input/output conditioning, headphone output, MIDI and USB protection, power sequencing, user-control chains, and mechanical constraints in one coherent design.

**Implementation highlights:**

- Hierarchical KiCad main-board project with dedicated functional sheets.
- Cirrus Logic CS4265 stereo codec with I2S, I2C, reset, ADC, and DAC signal paths.
- Separate analog and digital supply treatment with ferrite-bead/decoupling notes.
- Main-board title block identifies revision 3.0, 12 V input, and up to 500 mA USB output power.
- Dedicated audio inputs, audio outputs, headphone, MIDI, USB, power, control, and mechanics sheets.
- Controller-board source represented by an Altium `.PrjPcb` project.
- Grouped bottom-board BOM generated from KiCad: 318 components, with footprints and many manufacturer part numbers.
- Interactive HTML/iBOM-style material and design-library assets are present.

**Hardware/electronics notes:**

- Root README explicitly states that schematics and PCB design files are provided and editable with KiCad.
- `bottom-board.kicad_sch` and hierarchical sheets were directly parsed.
- `audio-codec.sch` directly identifies the CS4265-CNZ codec and I2S/I2C routing.
- The grouped BOM was directly parsed and identifies a 318-component main board.
- A direct fetch of the expected `bottom-board.kicad_pcb` path returned an empty payload in this connector run. The repository may still contain the board through a large-file/history/storage mechanism, but the PCB layout itself was not internally inspected here.
- No top-level LICENSE file was found. Open visibility is not equivalent to an open-hardware license.

**Hardware modifiability:** editable hierarchical KiCad schematic source verified; KiCad project source verified; BOM verified; controller-board Altium project path verified; PCB design files claimed by repository but main-board PCB payload not parsed; mechanical sheet present; enclosure source not deeply audited; license not verified.

**Platform relevance:** very high as a productization reference for a custom pedal workstation, multi-FX, desktop processor, or Linux/SBC-based groovebox. The design is more useful as a block-level and circuit-detail mine than as a directly cloneable board.

**Adaptation ideas:**

- Extract the CS4265 analog/I2S section and compare it against TAC5212, PCM3060, CS4272, and SGTL5000 front ends already mined.
- Reuse the functional partitioning for a modern STM32H7/Daisy/CM4 multi-FX platform with separate processor, codec/I/O, and control boards.
- Mine the MIDI, USB, headphone, and protection sheets as review references for the current pedal concepts.
- Build a reduced two-board architecture: audio/power I/O baseboard plus replaceable DSP/control module.
- Preserve the explicit mechanics sheet and BOM discipline in future custom hardware repositories.

**Quick engineering assessment:** the strongest electronics reference today, but not the cleanest reuse candidate. It would rank first on commercial-product hardware depth alone; it ranks second because license status and direct PCB-layout verification remain unresolved.

**Caveats / verification gaps:**

- No repository license was verified; commercial adaptation should be treated as prohibited/unclear until permission is established.
- The design dates and BOM indicate a 2021–2023 hardware generation; component availability needs a current lifecycle check.
- Main-board PCB layout was not parsed in this run.
- The processor/core-board software stack, boot flow, latency, and current buildability were not audited.
- A full manufacturing package and enclosure/tooling path were not verified.

### 3) [GaudiLabs/OpenTheremin_V3_Shield + firmware](https://github.com/GaudiLabs/OpenTheremin_V3_Shield) — **PASS**

**Lane:** standalone expressive instrument / RF-proximity sensor plus embedded wavetable synth.

**Technical summary:** Open.Theremin V3 is an Arduino UNO shield that implements a complete theremin instrument. Two antenna/heterodyne sensing channels measure pitch and volume hand position; the Arduino performs linearization/filtering and wavetable synthesis; on-board DAC circuitry generates the audio output. Hardware and firmware are split into dedicated repositories.

**Why it matters:** This project is valuable because the instrument interaction, analog sensing, calibration, DSP/control logic, and audio generation are inseparable. It is a better embedded-instrument reference than another MIDI keyboard or dev-board synth, especially for expressive sensors, mixed-signal design, oscillator stability, calibration, and unconventional musical interfaces.

**Implementation highlights:**

- Arduino UNO shield form factor.
- Dual heterodyne oscillator architecture for pitch and volume antennas.
- 4069 inverter oscillator circuitry and 74HC74 digital conditioning/division path.
- MCP4921 and MCP4922 SPI DAC devices visible in the schematic.
- Four panel potentiometers, push button, antenna connectors, and 3.5 mm output.
- Firmware uses hardware SPI and DAC latch timing to reduce audio jitter.
- Wavetable tone generation, pitch linearization/filtering, register transposition, and volume-response shaping.
- Separate source-hardware and firmware repositories.

**Hardware/electronics notes:**

- `PCB/OpenThereminCC.sch` was directly parsed as editable KiCad/Eeschema source.
- `PCB/OpenThereminCC.kicad_pcb` was directly parsed: two copper layers, 109 modules, 53 nets, and 1,031 routed tracks in the checked revision.
- Gerber outputs are present.
- The hardware README explicitly states that schematic, PCB design, and BOM are provided.
- A GPLv3 LICENSE file is present in the shield repository; the firmware repository also declares GNU licensing. GPLv3 is usable but is a software-oriented license rather than a purpose-built open-hardware license.

**Hardware modifiability:** editable KiCad schematic present; editable KiCad PCB present; project/source libraries present; Gerbers present; BOM claimed; firmware source present; enclosure/mechanical source not verified; GPLv3 present.

**Platform relevance:** medium for conventional pedals/synths, high for expressive-instrument and sensor-front-end work. Its mixed-signal lessons are more reusable than its Arduino UNO compute platform.

**Adaptation ideas:**

- Replace the UNO with RP2350, Teensy 4.1, or STM32 while retaining the analog oscillator/front-end concept.
- Add automatic calibration, temperature drift characterization, and stored linearization tables.
- Produce MIDI 2.0/MPE, CV/gate, or OSC output alongside the local synth engine.
- Replace the DAC/output stage with a modern low-noise audio codec or differential DAC path.
- Adapt the proximity front end to gesture control for a desktop synth or multi-FX pedal.

**Quick engineering assessment:** a mature, source-complete instrument reference with strong analog/interaction value. It ranks below the newer entries because the Arduino UNO platform and 2016-era hardware constrain direct product reuse.

**Caveats / verification gaps:**

- Old MCU platform and toolchain.
- Antenna geometry, environment, temperature, and RF coupling materially affect performance; calibration evidence was not deeply audited.
- BOM file itself was not parsed even though the README states it is included.
- GPLv3 may be awkward for hardware documentation compared with CERN-OHL/TAPR/CC BY-SA.
- No enclosure/antenna mechanical design source was verified.

**Sources:**

- [OpenTheremin V3 firmware](https://github.com/GaudiLabs/OpenTheremin_V3)
