## 1. MIDI / Control-Plane Determinism Audit — **RECOMMENDED**

### Verified facts

`plantssystem/KOSMOS2` runs a four-part RP2350 generative instrument around PRA32-U2/M. Its current architecture separates Core0 UI/logic, pattern generation, randomization, MIDI Clock and LCD work from Core1 synthesis through a MIDI event queue. It accepts full per-channel MIDI CC pass-through and generates 24-PPQN MIDI clock. On **2026-08-31**, commit `c49eee896955dd8ca0c2fcd2bf69b0de323ca656` fixed a Part-D density issue.

Primary sources:
- https://github.com/plantssystem/KOSMOS2
- https://github.com/plantssystem/KOSMOS2/commit/c49eee896955dd8ca0c2fcd2bf69b0de323ca656

### Engineering inference

Small instrument teams routinely validate the synth engine but do not characterize the **control plane under stress**. A useful paid audit should therefore measure:

- MIDI clock period jitter and phase error;
- Start / Stop / Continue handling;
- simultaneous CC burst behaviour;
- event-queue high-water mark and dropped messages;
- control/UI work versus audio deadline interaction;
- ownership conflicts between physical controls, MIDI and remote UI;
- reconnect/recovery behaviour;
- one-hour transport + CC soak.

This can become a module of the existing `RP2350-AUDIO-QUAL-001`, rather than spawning another unrelated consultancy product.

### Estimate

- Personal fit: **9.8/10**
- Feasibility: **9/10**
- Capital: **CHF 50–300**
- First paid audit: **1–3 weeks**
- Audit price: **CHF 1,200–2,500**
- Remediation package: **CHF 2,500–5,000**
- Plausible annual niche potential: **CHF 15k–45k**

### Main risks

Measurement quality depends on a trustworthy timestamp/timebase. USB host/device scheduling can dominate results. Platform-specific queueing behaviour limits portability of fixes. A synthetic MIDI flood can also produce impressive charts while failing to represent a real stage workload, humanity having already invented enough benchmarks that reward the benchmark rather than the product.

### Concrete 7-day action

Create `MIDICTRL-001.md` with:

1. 24-PPQN jitter histogram;
2. transport state tests;
3. 1× / 4× / 16× CC burst profiles;
4. queue watermark/drop counter;
5. physical-control + MIDI ownership collision tests;
6. UI/display stress delta;
7. 60-minute soak;
8. PASS/HOLD criteria.

## 2. Artist-Specific Signature Pedal Firmware Sprint

### Verified facts

`tronstoner/NitroTron3` is a Daisy Seed + Cleveland Music Co. Hothouse bass pedal built around three strongly differentiated modes: envelope/pitch-tracked harmonic companion, granular/spectral texture engine, and dynamic filter/distortion/synth voice. The project has a global 24-slot preset system, web updater, source build path, tagged release binaries plus SHA-256 files, and separate guitar/bass build profiles. Release `v0.5.1` was published on 2026-07-22.

The official Hothouse DSP pedal kit currently lists at **US$119**, supports Seed3, and is open-source hardware under CC BY-SA 4.0, making it a credible standard carrier for commissioned firmware prototypes without immediately funding a custom PCB.

Primary sources:
- https://github.com/tronstoner/NitroTron3
- https://github.com/tronstoner/NitroTron3/releases/tag/v0.5.1
- https://clevelandmusicco.com/hothouse-diy-digital-signal-processing-platform-kit/

### Engineering inference

There is a plausible boutique service between “write me an effect” and “design me a pedal company”: translate an artist's **2–3 actual playing behaviours** into a bounded firmware product on an existing Daisy carrier, with macro controls, preset migration, updater, release assets and acceptance audio clips.

The deliverable should be a productized firmware release, not a folder containing source code and optimism.

### Estimate

- Personal fit: **9.5/10**
- Feasibility: **8.5/10**
- Capital: **CHF 120–450** plus Daisy if needed
- First revenue: **2–4 weeks**
- Three-mode firmware sprint: **CHF 1,500–3,500**
- Additional mode: **CHF 500–1,000**
- Optional production model: NRE + **CHF 15–30/unit** licence/support royalty
- Plausible annual potential: **CHF 15k–50k**

### Main risks

Subjective acceptance criteria, artist-name/trademark permissions, hardware support burden, third-party GPL code boundaries and the temptation to implement a whole album's signal chain instead of three testable behaviours.

### Concrete 7-day action

Build a one-page **Signature Pedal Sprint specification** with three fictional/non-branded modes, six controls, preset behaviour, hardware target, acceptance clips and explicit “not included” scope.

## 3. Constrained AI Preset & Sound-Design Data Engine

### Verified facts

`bbw1081/DaisySeed-MultiFXPedal` uses a structured preset representation containing a name, effect list and parameter arrays. Its current effect catalog includes delay, reverse delay, pitch shift, chorus, flanger, phaser, reverb, EQ, tremolo, wavefolder and several distortion families. The repository was pushed on 2026-08-28 and received an ordered parts list on 2026-08-26.

Its companion `bbw1081/Guitar-Preset-AI` explicitly states that the text-to-preset model **does not work very well yet because it needs much more training data** and currently accepts only text descriptions. This is unusually valuable evidence because the failure mode is written down instead of being renamed “beta intelligence”.

Primary sources:
- https://github.com/bbw1081/DaisySeed-MultiFXPedal
- https://github.com/bbw1081/Guitar-Preset-AI

### Engineering inference

The commercial problem is not “train a bigger model”. It is the missing **sound-design data and validity layer**:

- typed parameter schema with units and safe ranges;
- effect-combination rules;
- synthetic preset generation with constraints;
- human A/B rating loop;
- optional rendered-audio embeddings;
- parameter repair/validation before deployment;
- provenance and versioned datasets.

A deterministic validator should always sit between the AI output and the pedal.

### Estimate

- Personal fit: **9.4/10**
- Feasibility: **7.5/10**
- Capital: **CHF 0–300**
- First revenue: **2–5 weeks**
- Data/schema PoC: **CHF 1,500–3,000**
- Integrated generator + validator + UI: **CHF 4,000–8,000**
- Ongoing model/data tuning: **CHF 300–800/month**
- Plausible annual potential: **CHF 15k–40k**

### Main risks

Small datasets, subjective labels, distribution shift between guitars/amps, unsafe parameter combinations, questionable value versus a good search/curation UI, and GPL contamination if reference implementations are copied rather than independently designed.

### Concrete 7-day action

Create `PresetConstraintSchema v0.1` for the existing multi-FX direction, then compare:

1. unconstrained LLM generation;
2. schema-constrained generation;
3. constraint + retrieval from 50–100 human-labelled presets.

Measure valid-output rate and human preference instead of celebrating a convincing adjective.

## 4. Embedded FM Patch Migration / Compatibility Pack

### Verified facts

`Saisana299/Cranberry-Synth` is a Teensy 4.1 6-operator FM synth with **32 algorithms, 16 voices, 16 MIDI channels, 4-rate/4-level envelopes, key/velocity scaling, LFO, effects, PCM1802 audio input, quad I2S output, OLED UI and SD playback**. The project specifies 44.1 kHz, 16-bit output / Q23 internal processing and approximately 2.9 ms latency. It is GPL-3.0 and cites Dexed as an algorithmic reference.

Primary source:
- https://github.com/Saisana299/Cranberry-Synth

### Engineering inference

A useful commercial add-on for embedded FM products is not another oscillator. It is the tedious compatibility layer around patches:

- SysEx / patch import-export;
- 32-algorithm mapping;
- envelope-rate/level translation;
- keyboard level scaling;
- detune/fixed-ratio mapping;
- validation and round-trip tests;
- preset metadata and browser/desktop converter.

This is niche, but it converts an embedded FM demo into something musicians can actually migrate to.

### Estimate

- Personal fit: **8.7/10**
- Feasibility: **8/10**
- Capital: **CHF 0–200**
- First revenue: **2–5 weeks**
- Integration project: **CHF 1,500–4,000**
- Optional standalone converter: **CHF 29–79**
- Plausible annual potential: **CHF 8k–25k**

### Main risks

FM parameter semantics differ subtly between engines. Exact DX-style behavioural compatibility can become a deep test problem. Trademark/IP wording needs care, and perceptual equivalence is harder than bitwise round-trip equivalence.

### Concrete 7-day action

Implement one **single-voice patch round-trip test fixture** with canonical JSON plus a mapping table for operator frequency, level, envelope and algorithm topology. Do not begin with all SysEx variants at once.
